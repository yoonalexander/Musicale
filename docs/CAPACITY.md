# Capacity and service limits

Reviewed October 16, 2026 against the linked provider documentation. These are published allowances and local observations, not measured production capacity, guaranteed uptime or confirmed account dashboard settings.

| Surface                    | Published/documented boundary                                                                                                                    | Musicale operating choice                                                                                                                                                    |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| App write budgets          | PostgreSQL tests enforce ten vote attempts/account/minute, five profile changes/minute and thirty admin attempts/minute                          | These protect integrity; they do not prove resistance to all traffic or abuse.                                                                                               |

The planned beta is three to twenty-five people, with roughly one saved vote per person/day. This is a planning assumption, not observed traffic. Review capacity if sign-in demand, long-lived leaderboard tabs, database size or errors approach the boundaries above. Do not upgrade by default; inspect actual measurements first.

The Phase 5 regression run accepted **50 of 50 concurrent distinct-account votes, zero errors, 30,557 ms** on a busy Windows computer running several local projects. Ratings remained zero sum and accepted records were retained. This is one constrained local observation, not a requests-per-second benchmark or hosted latency claim. The original Phase 3 evidence retains its separate workload observation; do not combine elapsed times across different runs as a capacity estimate. Phase 4 tests enforce a local five-second cross-browser refresh bound; hosted timing still needs verification.

Phase 6 verification will append its current measured burst and restore results to PHASE_6.md. No load is generated against production, and no paid service was enabled.
